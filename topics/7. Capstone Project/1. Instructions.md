# Capstone Project Instructions

## 1. Overview

The Capstone Project is the final phase of the course, designed to consolidate your learning by building a complete software application.

- **Duration**: 8 sprints (1 week per sprint).
- **Team Size**: 3-5 members per team.
- **Methodology**: Scrum/Agile.

## 2. Process & Timeline

| Sprint | Phase | Focus | Activities | Deliverables | Scrum Events |
|--------|-------|-------|------------|--------------|--------------|
| 1 | Inception | Project Setup & Planning | Team formation, Topic selection, Requirement Analysis (User Stories, Use Cases) | SRS Document, Product Backlog on PM Tool (Jira/Trello/GitHub Projects) | Sprint Planning |
| 2 | Inception | Design & Infrastructure | Database Design (ERD), Architecture Design, Setup Infrastructure (Git, CI/CD, Project Skeleton) | Design Documents (ERD, Class Diagram, Architecture Diagram) | Sprint Planning, Review, Retro |
| 3 | Core Features | Authentication & User Management | Implement Authentication, User Management, basic CRUD operations | Working Auth module, User Management module | Sprint Planning, Daily Standup, Review, Retro |
| 4 | Core Features | Main Business Logic | Implement main business logic basic flow, API endpoints | Core business features functional | Sprint Planning, Daily Standup, Review, Retro |
| 5 | Advanced Features | Feature Expansion | Expand business features, Reporting, Search/Filter | Additional business features, Reports | Sprint Planning, Daily Standup, Review, Retro |
| 6 | Advanced Features | Integration & Optimization | Integration between modules, performance optimization, advanced queries | Integrated system, optimized queries | Sprint Planning, Daily Standup, Review, Retro |
| 7 | Finalization | Testing & Polish | UI/UX improvements, validation, bug fixing, testing, deployment | Tested & deployed application | Sprint Planning, Daily Standup, Review, Retro |
| 8 | Final Presentation | Demo & Defense | Prepare presentation, final demo, documentation wrap-up | Presentation Slides, Final Documentation, Live Demo | **Final Presentation** |

## 3. Deliverables

All teams must submit the following artifacts. We strongly encourage **AI-first formats** — plain-text, version-controllable formats that can be read, generated, and reviewed by both humans and AI tools (e.g., GitHub Copilot, ChatGPT, Claude).

### Why AI-First Formats?

- **Version Control Friendly**: Plain-text formats produce meaningful diffs in Git, making code review and history tracking effective.
- **AI-Readable & Generatable**: AI assistants can directly read, generate, and validate plain-text artifacts — enabling faster iteration and automated quality checks.
- **Portable & Lightweight**: No proprietary software required to view or edit. Works everywhere — IDEs, terminals, CI/CD pipelines.
- **Single Source of Truth**: Embed diagrams and tables directly alongside code and docs in the same repository, reducing drift between artifacts.

### Deliverables Table

| # | Deliverable | Traditional Format | AI-First Format | Guide |
|---|---|---|---|---|
| 1 | **Source Code** | — | Git repository (GitHub/GitLab) | Proper commit history, branching strategy, PR-based workflow |
| 2 | **SRS** (Software Requirements Specification) | `.docx`, `.pdf` | **Markdown** (`.md`) | Write as structured `.md` with headings, user stories, and acceptance criteria. Render to PDF if needed via Pandoc |
| 3 | **SDD** (Software Design Document) | `.docx`, `.pdf` | **Markdown** (`.md`) | Include architecture overview, component descriptions, and design decisions in `.md` |
| 4 | **ERD** (Entity-Relationship Diagram) | `.png`, `.drawio` | **DBML** ([dbdiagram.io](https://dbdiagram.io) format) | Define tables and relationships in `.dbml` — renderable on dbdiagram.io, version-controllable in Git |
| 5 | **Architecture / Class / Sequence Diagrams** | `.png`, `.drawio`, `.vsdx` | **Mermaid** or **PlantUML** | Embed directly in Markdown using fenced code blocks (e.g., ` ```mermaid `). Renders natively on GitHub |
| 6 | **API Documentation** | Manually written `.docx` | **OpenAPI / Swagger** (`.yaml`) | Auto-generate from code annotations (Springdoc). Serves as both documentation and contract |
| 7 | **Data Samples / Seed Data** | `.xlsx`, `.docx` | **CSV** (`.csv`) | Store tabular data as `.csv` — easily diffable, importable, and processable by scripts and AI |
| 8 | **User Manual** | `.docx`, `.pdf` | **Markdown** (`.md`) | Write in `.md` with screenshots. Can be hosted as a static site (GitHub Pages, MkDocs) |
| 9 | **Project Report** | `.docx` | **Markdown** or **LaTeX** (`.md` / `.tex`) | Use Markdown for simplicity or LaTeX for formal submissions. Both support PDF export |
| 10 | **Presentation Slides** | `.pptx` | **Markdown-based** (Marp, reveal.js) or `.pptx` | Markdown slides via [Marp](https://marp.app) for version control; traditional `.pptx` is also acceptable |
| 11 | **Deployed Application** | — | Live URL | Provide link to deployed app (e.g., Render, Railway, AWS, Heroku) |
| 12 | **Sprint Backlog & Tracking** | Spreadsheet | **Project Management Tool** | Use Jira / Trello / GitHub Projects. Export backlog as `.csv` for archival |

## 4. Evaluation Criteria

- **Functionality (40%)**: Completeness of features, logic correctness.
- **Technical Quality (30%)**: Code quality, architecture, database design, security, performance.
- **Process & Teamwork (20%)**: Adherence to Agile, Git usage, collaboration.
- **Documentation & Presentation (10%)**: Clarity of artifacts and final demo.
